# Развёртывание самостоятельной версии

Готовый серверный комплект предназначен для Linux x86-64 с Docker Engine, Compose v2, Python 3 и HTTPS reverse proxy. Скачайте архив выпуска, сверьте SHA-256 и извлеките его в новый каталог.

Выполняйте команды из `public/deploy`. База создаётся пустой: без пациентов, обследований и интеграций. Не используйте существующие базы или тома другого приложения. Внутренние имена переменных и базы сохранены для совместимости протокола.

## Первый запуск

Из корня распакованного комплекта загрузите готовый образ.

```sh
docker image load -i colposcopy-server-image.tar
cd public/deploy
python3 configure.py
# private имеет режим 0700. Локальный Compose монтирует secrets с правами
# исходных файлов: read-only доступ внутри контейнеров нужен postgres/app.
# Каталог 0700 защищает эти файлы от других пользователей хоста.
chmod 0444 private/*
# Генератор PKCS8 ничего не печатает и не перезаписывает файл.
docker run --rm --user "$(id -u):$(id -g)" \
  --entrypoint /usr/local/bin/server \
  -e M53_OFFLINE_SIGNING_KEY_FILE=/keys/offline_key \
  -v "$PWD/private:/keys" colposcopy-public:local generate-offline-key
chmod 0444 private/offline_key
docker compose up -d db
# Дождитесь healthy через docker compose ps.
# Только миграционная роль; пароль не попадает в аргументы psql.
python3 migration_sql.py > private/migrations.sql
docker compose exec -T db sh -c 'export PGPASSWORD="$(cat /run/secrets/migrator_password)"; exec psql -X -v ON_ERROR_STOP=1 -h 127.0.0.1 -U colposcopy_migrator -d m53colpo' < private/migrations.sql
rm private/migrations.sql
```

Не запускайте server до завершения миграций. Для повторного обновления используйте ту же команду миграции после остановки server и резервного копирования. Применённый файл с другим SHA-256 вызывает отказ. Не изменяйте историю миграций. Обновления выполняются администратором вручную, после проверки совместимости клиента и сервера.

Создайте собственные UUID организации, врача и рабочего места, например через `python3 -c 'import uuid; print(uuid.uuid4())'`. Передайте их вместо синтетических значений ниже. Логин и имена задаются явно, пароль и ключ читаются из файлов; команда не выводит их:

```sh
docker compose run --rm \
  -e M53_ORGANIZATION_ID=11111111-1111-4111-8111-111111111111 \
  -e M53_ORGANIZATION_NAME='Учебная организация' \
  -e M53_DOCTOR_ID=22222222-2222-4222-8222-222222222222 \
  -e M53_DOCTOR_NAME='Учебный врач' \
  -e M53_USER_LOGIN=doctor \
  -e M53_WORKSTATION_ID=33333333-3333-4333-8333-333333333333 \
  -e M53_WORKSTATION_NAME='Учебный кабинет' \
  admin init-standalone
docker compose up -d server
curl --fail http://127.0.0.1:8787/health
curl --fail http://127.0.0.1:8787/ready
```

`init-standalone` создаёт самостоятельную организацию, врача, вход, рабочее место и шаблон отчёта. Словарь этим действием не создаётся. Повторный вызов не является сменой пароля или ключа. Для дополнительных кабинетов используйте отдельные UUID и отдельные ключи; не раздавайте один профиль всем компьютерам. Не запускайте demo seed и команды внешних интеграций.

## Словарь и допуск к утверждению

До работы врача импортируйте подготовленный и проверенный вашей организацией словарь в формате `Catalog` (см. `crates/server/src/terminology.rs`). Например, сохраните файл в `private/catalog.json` и выполните:

```sh
docker compose run --rm -v "$PWD/private/catalog.json:/catalog.json:ro" admin import-terminology /catalog.json
```

Импорт устанавливает `clinically_approved=false`; сам по себе он не разрешает утверждение протокола. После отдельной проверки содержимого уполномоченным специалистом подготовьте `private/review.json`: ровно `version_id` импортированной версии и `content_sha256` — SHA-256 исходных байтов JSON в нижнем регистре. Затем выполните:

```sh
docker compose run --rm -v "$PWD/private/review.json:/review.json:ro" admin approve-terminology /review.json
```

Команда принимает только точное совпадение версии и SHA-256 импортированного словаря. Не подменяйте рассмотренный файл между импортом и согласованием. Эта административная отметка не является внешним медицинским допуском; учебный пример словаря также не является таким допуском.

## HTTPS и привязка клиента

Сервер слушает только loopback хоста. Порт PostgreSQL также опубликован только на loopback; не открывайте его в межсетевом экране. Reverse proxy на том же хосте должен проксировать HTTPS на `http://127.0.0.1:8787`, поддерживать долгие SSE-соединения и загрузку фотографий. Установите ограничения размера/таймаутов, достаточные для ваших файлов, и исключите запись тел запросов и заголовков авторизации в журналы.

Используйте принадлежащее организации DNS-имя и сертификат, которому доверяет система клиента. Для закрытой сети распространите корневой CA средствами администратора; отключать проверку сертификата нельзя. Проверьте с рабочего места полную цепочку сертификата и доступность health/ready по HTTPS. HTTP допустим для локальной диагностики loopback, не для удалённой работы врача.

Установите клиент Windows или Linux по инструкции выпуска. В настройке соединения укажите собственный HTTPS URL и ключ рабочего места, затем логин врача и пароль. Ключ из `private/workstation_key` и пароль из `private/doctor_password` передайте защищённым каналом; не помещайте их в публичный ZIP, Git, скриншоты или команды. Детали полей профиля смотрите в инструкции конкретного клиентского выпуска. Автообновление отсутствует.

В Compose включены подписанные автономные разрешения сроком до 30 дней. Ключ подписи необходимо сохранять вместе с резервной копией; его утрата не исправляется копированием профиля. Первичный вход требует онлайн-соединения.

При сетевой эксплуатации изменённой версии опубликуйте для её удалённых пользователей заметную ссылку на бесплатное получение исходного кода именно этой сборки. Это условие раздела 13. [AGPL-3.0](../../LICENSE)

## Резервная копия и восстановление

Согласованная копия включает PostgreSQL, assets, private, исходники/образ того же выпуска и настройки reverse proxy. Каталог копий должен быть вне публичного веб-каталога, с шифрованием и ограниченным доступом. Остановите server, чтобы между дампом и архивом assets не появились новые ссылки:

```sh
umask 077
mkdir -p backups
docker compose stop server
docker compose exec -T db pg_dump -U postgres -d m53colpo -Fc > backups/database.dump
docker compose run --rm -T --no-deps --entrypoint tar server -C /assets -czf - . > backups/assets.tgz
tar -czf backups/private.tgz private
docker compose start server
```

При ошибке любой команды не считайте копию готовой. Сохраните контрольные суммы и проверьте восстановление отдельно. На новом изолированном хосте восстановите private с каталогом 0700, установите тот же образ, создайте пустые тома и запустите только db. Скрипт init создаст роли. Затем восстановите дамп и assets:

```sh
docker compose exec -T db pg_restore -U postgres -d m53colpo --exit-on-error --clean --if-exists < backups/database.dump
docker compose run --rm -T --no-deps --entrypoint tar server -C /assets -xzf - < backups/assets.tgz
docker compose up -d server
curl --fail http://127.0.0.1:8787/ready
```

Эти команды предназначены только для нового восстановительного стенда: `--clean` удаляет совпадающие объекты. Не направляйте их в рабочую БД. После восстановления проверьте вход, фотографии, утверждённый PDF и новый синтетический черновик. `docker compose down -v` удаляет данные и для обычной остановки не используется. Секреты суперпользователя и мигратора не монтируются в server.
